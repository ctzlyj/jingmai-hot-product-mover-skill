# 逐项取整的严格到手价

## 触发与已复现问题

用户明确要求先分别将活动直降金额、国补金额四舍五入到分，再从京东价扣减时使用本口径。目标倍率、折扣率与源价时点仍以当前用户授权为准；不改变其他任务的默认定价模式。

将目标价直接除以两个净折扣率，只适用于最后统一取整的模型，不与逐项取整严格等价。例如目标到手价 79.06 元、直降与国补均 15% 时，直接相除得到京东价 109.43 元；直降 16.41 元、国补 13.95 元，实际按本公式复算为 79.07 元。京东价 109.42 元才会在此例中得到 79.06 元。

## 复用已有能力

数学实现复用 `jd-competitor-price-adjustment-skill/scripts/jd_price_adjustment.py` 已验证的纯金额函数，以冻结快照随本仓库的 `scripts/component_rounded_pricing.py` 分发。调用本仓库的 `calculate_final_price` 和 `create_price_plan`，不再依赖用户家目录或旁边另装的 Skill，不降级为简单除法，也不在搬运流程另写一套算法。

打包前已复现：本机全套测试通过，但复制到无其他 Skill 的干净目录后，补发模块导入报 `ModuleNotFoundError: No module named 'jd_price_adjustment'`。根因是未声明的本机路径依赖，且原依赖仓库的已提交版本没有当前所需的 `target_gap` 参数，不能让安装者下载旧版冒充可用依赖。

纯函数快照来源文件 SHA-256 为 `087e8db49805be0e6bb7dc08d8e85b6128ca8f893f4126d024bc3704cee36c11`；首次分发模块 SHA-256 为 `63d7ab7f79392d9914d04936e0292acdba24ff4df2c9a5205945a9b44d837d8e`。仅携带金额数据类、异常及其函数依赖，不打包原 Skill 的业务取数、店铺信息、配置或写入逻辑。公式及求解选择保持不变。

零优惠券的当前流程：

1. 从已核实的逐 SKU 源价计算目标价。PDD 两倍目标必须显式乘 2，不套用比价模式默认减 0.10 元。
2. `calculate_final_price(current_jd_price, direct_rate, subsidy_rate)` 分别计算 `ROUND_HALF_UP` 到分的直降、国补及最终到手价。国补基数为 `京东价 × (1 - 直降比例)`，不是减去已取整直降金额后的余额。
3. 已精确达标的 SKU 保持原京东价，避免仅因存在另一组解而产生额外写入。
4. 不达标的 SKU 调用 `create_price_plan(target_arrival, direct_rate, subsidy_rate, target_gap=Decimal("0"))`。此处第一个参数传已经算好的目标到手价，显式清除该函数的默认比价差额。该函数按分搜索精确解，不把近似解当成通过。
5. 用户更换为非零优惠券、国补计算基数或其他公式时，本零券流程不再适用；先验证新的公式与反推能力。

## 写入与验收

- 价格表、请求体及哈希绑定到当前授权，保留更新前价格和回滚请求。公式变化会使旧请求授权失效，必须取得针对新公式和作用范围的授权。
- 使用已有 `jdo-product-update` 的 `SkuJdprice` 原子更新，不提交库存或整版编辑；每次写前回查指定 Profile 的店铺身份。
- 先单条实测，再小批量验证。提交后核对申请单，再回查线上京东价；已接受但待传播的请求只查询，不重复提交。
- Windows 原子保存审计文件遇到共享占用错误 `WinError 32/33` 时，只对本地文件替换做有上限的退避重试，不能重试业务写请求或降级为直接覆盖。若 API 已返回成功但状态落盘失败，先用持久化回执、申请单和线上价确认，再恢复状态；保留恢复证据，不因状态仍是 `SUBMITTING` 就再次改价。重试耗尽或证据不一致时停止。
- 最终对完整目标批次独立读取线上价，逐 SKU 重新计算两个优惠金额与到手价；分别记录“京东价与请求一致”和“逐项取整后到手价与目标一致”。任何一项有分差都不能声称严格定价完成。
- 身份、SKU 映射、已确认请求、预期旧价或非价格字段发生意外变化时停止。无精确分位解时停止该批写入；回滚需另行授权。
- 这证明给定公式下的计算结果，不证明已报名活动或消费者实际结算价已同步；不自动改活动。
