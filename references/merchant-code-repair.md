# 当前商家编码核对与已有链接纠码

## 已复现的问题

- 原始发布归档的编码为空，后续商家在当前商品文件夹表格补填编码。只读旧归档、按旧自动码克隆A/B，会把错误码复制到新链接，影响发货。
- 不能把“读不到当前盘符”表述为“商家没有填”。先恢复当前数据源；读取当前表并保存来源路径、SHA-256、行号和完整销售属性。
- 单商品内重复编码可能对应不同款式，不能通过自动加后缀、补零或改字母处理。A/B对应SKU共用商家码是用户明确目的，不要求全店唯一。

## 当前表是来源依据

商家补码后出现损坏ZIP、规格错字修正或删除原选项时，先读 `current-workbook-recovery.md`。不要把网络盘旧长度缓存当作表内缺码，也不能让缺行SKU混入已确认编码数量。

`scripts/jdo_merchant_code_repair.py:match_workbook` 复用当前表解析器，按完整来源销售属性匹配，而非当前行号、旧码后缀或尺寸排序。源导出首列为尺寸时，使用原解析器的同一维度交换规则。拒绝空码、公式码、重复规格、重复商家码和规格集合不一致。

`scripts/pdd_ab_image_publish.py prepare` 必须提供 `--source-root`，读取每个来源文件夹的当前表。`template_with_current_codes` 用表码刷新仅供准备的旧模板，核验A中该码对应的款式/尺寸，再生成B草稿；不写A。当前表与A冲突则停止，纠正A必须另有明确授权。计划绑定当前表哈希，旧计划无该证据时不能用于新增B；不能用缓存绕过当前表核对。

## 官方接口与安全编辑

1. 优先发现官方窄字段更新能力。POP原子PATCH实测拒绝 `SkuVendorSku`（参数校验失败、组件不支持）；保留错误后不要对整批重复发送同一种无效请求，更不能换组件名绕过白名单。
2. 本地可复用的 `make_full_edit` 使用官方已有商品整版编辑，并从实时详情重建本次支持的组件；不支持的组件立即报错。携带现有 `productId`、全部现有 `SkuId`/`SkuUUid`，`saveActionType=0`，禁止任何 `SkuStockNum`。
3. 完整保留实时SKU价格、启用状态、短标题、规格ID及别名、款式主图组、公共主图和详情图；其他已支持组件也从实时详情取值，不从旧发品体带回旧价格。模板仅限定已审核支持的组件集合。
4. **必须按销售属性 `indexId` 和 `attrValuesSeqNo` 排列SKU**。详情接口返回顺序不稳定，按其原始数组顺序整版编辑会重排前台规格；已真实复现，并通过排序修复、规格顺序回读及回归测试验证。不得只比较别名集合而忽略顺序。
5. 编辑前保存实时详情、库存专用接口结果、目标码映射、请求体及回滚体。绑定完整计划摘要和用户已有明确纠码授权；这不是新增商品，不要求用户再次输入发品确认字符串。先单SKU、再十SKU验证，再扩量。
6. 校验接口通过后才提交。保存申请ID并分别回读申请单及线上详情，逐SKU确认目标码。结果不明只读恢复，不能盲重发。回滚体仅供有证据的修复或人工回滚，不自动反复写入。
7. 线上逐SKU核对价格、规格顺序和ID、图片、状态；库存以专用接口为准。整版编辑可能刷新SPU汇总价为现有SKU最高价，并新增默认 `mobileDescUseFlag=0`；应单列平台派生字段变化，不能把实际SKU改价隐藏在该例外中。
8. 身份/鉴权异常、库存异常或连续系统性失败停止整批。用户要求单项失败跳过时保留ID、原因及未完成清单，不把提交成功当成最终生效。
