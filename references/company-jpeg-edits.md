# 公司生图 JPEG 恢复与复用

适用：用户选择公司 Flare/Sunburst 改已有链接主图，且 PNG 生图虽收到 HTTP 200，却发生响应截断（如 ChunkedEncodingError/IncompleteRead）。2026-10-11 同参考图、同定稿提示词、同客户端对照，PNG 失败、JPEG 成功；另一次单商品 5 张 JPEG 全成功，并完成上传和正式体/编辑体/SKU首图/列表封面独立回查。具体传输截断节点尚未确认，不应归因为 VPN、预算或提示词。后续真实批次确认 **JPEG 也可能响应截断**；单图成功不代表整批可靠性，不能把 JPEG 写成保证恢复的修复。

- 保持 `hot_replica_mode.build_dynamic_prompt(title)` 原文，不能为了恢复服务自行改提示词。
- 公司 `GPT-Image-2.5-Flare-joybuilder` 与 `GPT-Image-2.5-Sunburst-joybuilder` 可交替分配，共享最多 4 并发、每秒最多启动 1 请求；JSON `/images/edits` 明确指定 `output_format=jpeg`，输出使用 `.jpg`。参考图按真实格式发送，保留原字节。
- `scripts/company_jpeg_edits.py` 是独立公司生成适配器，不上传、不改品、不自动用外部平台。Key 只从当前进程 `JD_LLM_API_KEY` 读取。不要修改官方安装包。
- plan 含 `title`、用户定稿 `prompt` 与去重后的 `sources[]`：每项 `sha`（稳定素材标识）、`source`（已授权本地原图路径）、`model`（上述公司模型）。先 `--plan <plan.json> --output <任务输出目录> --dry-run`；再不带 `--dry-run` 实际生成。工具拒绝非定稿 prompt、外部模型、重复标识和不同计划复用旧输出目录。
- 一种款式不同尺寸共用同一结果；不同款式首图分别映射，重复后续图复用，不改变图序或 SKU 归属。用户只要求主图时不要改详情。
- `generation.json` 成功结果按 SHA256 校验复用。已尝试失败、请求开始后未取得结果都停止，不自动重放或换平台；先核对产出及计费。凭证/原始错误体不落日志。
- 上传仍走京麦官方 CLI，每次写前三要素身份核对。只提交图片组件，保持详情、标题、价格、库存、编码、类目、品牌和状态；一次 PATCH 后用正式体/编辑体核对全部图序与 SKU 首图，列表封面作附加确认。结果未知先回查，绝不重发。

验证：`python -m unittest discover -s tests -p test_company_jpeg_edits.py -v`，再 `py_compile` 与上述 dry-run；不因 HTTP 200 或本地生成成功声称店铺已替换。不做事后视觉返工，除非用户指出问题或平台驳回。

## 批量实测后的保护（2026-10-11）

- 用户定稿提示词、参考图和款式归属不变。缩小 JPEG 响应可降低传输体积，但不能保证不再断流；本次 `quality=low`、`output_compression=20` 为任务局部恢复设置，后续不要把 low 设为通用默认，也不擅自降低用户要求的画质。只缓存完整解码的原始模型输出，不能用截断图或本地贴图冒充结果。
- 批量上传与商品提交共用模块级京麦身份时，`configure_jdo_profile` 会清空已核验身份；并行刷新可使另一上传线程在写前报“尚未完成身份回查”。任务执行器用同一可重入锁串行身份刷新与京麦写操作，仍逐次实时核对三要素；不删除核对来换速度。公司图片生成仍共享四并发和每秒一次启动限流，不受这把写锁影响。
- 用户已授权外部回退时，公司模型拒绝的图片直接用外部 `gpt-image-2.5` 经 sufy-image2 补图，不再重复申请权限；只补失败图片，保留同一用户定稿提示词、同一原始参考图和款式归属，不改提示词绕过。公司额度双模型耗尽时也按用户既定外部回退规则执行。只选公司且未授权外部收费时才保持公司-only，不得把公司-only适配器限制误当成整项任务禁止外部。
- 公司成功图片不重做；外部请求用独立失败图账本与输出目录，保留公司失败回执。HTTP400明确拒绝与传输结果不明区分：传输未知先核对产出、请求日志及计费，外部502仅在确认未产出/未收费后单项恢复，不能重放成功任务或整批。京麦申请已更新但未生效仍是平台阻塞，换生图模型不授权重复商品提交。
- 编辑体会规范化属性顺序、字典展示别名、空 mappingId 与继承字段；正式体应严格核对业务字段，编辑体的图片与 SKU 归属仍须逐位核对。不要把展示归一化误判成修改价格/库存，也不要放宽真实品牌ID、SKU编码、销售属性值、状态或详情保护。
- `draftComputeStatus=3` 且正式体仍是旧图时，保留申请与回执并报告平台阻塞，不能算换图成功，也不因 apply 已变重复提交。正式图已变而列表封面仍旧时单独报告封面未刷新，不宣称封面成功。
- 本批最终结果按“全部换好、部分换好、未在线生效”独立输出。部分换好仅表示成功图已真实替换、失败槽位保留原图；不能冒充全部完成。需要剩余补图时沿用原产品ID、原素材与回执，不创建新链接、不复活已下架商品。

## 双模型并行吞吐（2026-10-19 实测修正）

Flare 与 Sunburst 可真正并行，不是共享 4 并发：两客户端各 4 并发、各自 1 req/s 启动限速，任务交替分配并固定各自首选模型（在官方客户端外包一层指定 chain 首位的子类，不改官方包）。实测吞吐约 760 张/h（单模型约 400 张/h，≈1.9 倍），218 张零失败、无 429。此前“两模型共享最多 4 并发”按保守配置理解即可；并行前先小批量确认网关再放量。

离线回归：`python -m unittest discover -s tests -p test_company_batch_guidance.py -v`，并跑完整 tests、`py_compile` 与公司生成器 dry-run。该维护只修正能力指引，不新增真实请求、账户配置或商品操作。

## 已验证的授权外部补图（2026-10-11）

本批公司拒绝图片按用户明确指令转外部 `gpt-image-2.5`，原版动态提示词和原图字节不变，45张全部生成并上传，21条链接中17条外部补图正式生效、4条仍被京麦申请挡住。1张外部502在同令牌只读消费日志确认44次成功计费和1次失败未计费后单项恢复；已成功的44张没有重做。非方形成品复用现有 `square_pad_image` 无裁剪方图兜底，保留原始成品和摘要；不为比例问题重新付费。

调用复用 sufy-image2 的 `SfImage2Client.edit`，明确模型与1:1尺寸，参考图按真实格式发送；外部凭据仅用当前用户DPAPI或进程环境，不保存明文。上传和补图PATCH前仍核对店铺三要素，使用最新正式体/申请体快照，只改对应失败图槽位，不覆盖成功图、不混款式、不改其他字段。

## 申请驳回原因读取（2026-10-11 实测修正）

- 申请列表 `scopeSet` 是请求枚举，不一定等于返回字段名：传 `keeperReason` 才返回 `auditReason`，传 `draftComputeStatus` 返回 `status`，传 `draftStatus` 返回 `pushStatus`。不要直接用返回字段名请求，否则原因会静默缺失；`jd_product_pipeline.product_apply_rejection` 已修正并有回归。
- `keeperStatus=309` / `status=300` 是已驳回，不是仍在等审核。先获取具体原因，不凭空猜测接口、网络或额度问题。验证接口成功不等于审核通过；只从提交回执、正式体和申请体判定生效。
- 原版提示词要求保留文字卖点，平台指出宣传词违规时两者可能冲突。只定位被驳回的宣传内容并给用户具体修正方案；提示词原文冻结时，须取得用户对该内容例外的明确指示。不得通过不断换接口、反复提交同一违规图片或隐瞒失败来宣称完成。
- 同一授权商品的原子图片申请确已失败时，可以用已验证的正式商品业务快照、原SKU身份及新图构造整版编辑恢复：先平台检测、`saveActionType=0`、不提交库存、逐项保护价格编码规格。恢复后仍严格回查；并非所有驳回都能靠整版编辑修复。
